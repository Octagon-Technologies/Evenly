## P0 — blocker (silent loss/corruption of money data in routine flows)

- [x] **1. Zone-2 mutations outside `editExpense`/`editBill` never advance `split_version`, so `merge_expense` reverts them on next sync.**
  Sites: `GroupRepositoryImpl.reconcilePlaceholder` (→ `ShareDao.reassignUserInGroup`, `ExpenseDao.reassignPayerInGroup`, `ExpenseDao.touchExpensesWithShareOfUser`), `GroupRepositoryImpl.addMemberToPastExpenses` (EVEN re-split), `GroupRepositoryImpl.resolveConflict` (include-with-share). All bump `row_version` only.
  Failure: reconcile a placeholder → real user → expense is dirty but `split_version == base` → server treats push as metadata-only, never applies the payer/share reassignment → returns canonical with the *placeholder* still in it → device reverts. Roster says claimed; every debt still points at the retired placeholder.
  Fix: make each site also set `splitVersion = splitVersion + 1, splitUpdatedBy = actor`. Don't push these shares via `pushDirty` or exempt from adoption instead.

- [x] **2. `currency` is Zone 2 per schema/CLAUDE.md but missing from `splitChanged` in `editExpense`; `editBill`'s `splitChanged` misses offsetting item/extras changes.**
  `ExpenseRepositoryImpl.editExpense` checks amount/mode/payer/shares, not `input.currency != existing.currency`. Currency is applied server-side only inside the `v_client_changed` branch of `merge_expense`.
  Failure: change a $30 USD dinner to €30 (digits unchanged) → push looks metadata-only → server keeps USD → edit silently reverts on the editor's own device. Similarly in `BillRepositoryImpl.editBill`: line A +$5 / line B −$5 (same count, same total) or an extras swap → `splitChanged=false` → same silent revert.
  Fix: add `input.currency != existing.currency` to the `editExpense` disjunction. Replace `editBill`'s `itemsChanged` heuristic with a content comparison (id → (quantity, lineTotal) map diff) and add an extras-tuple comparison. Don't move currency into Zone 1.

- [x] **3. Itemized-bill shares are a stale server snapshot; nothing rematerializes on pull — local-derived and server-synced models corrupt each other.**
  `materializeShares` never dirties the expense and has no trigger to re-run on pull. Server `shares` for a bill freeze at the last `splitChanged` edit (often the empty create set).
  Failure (a): a Zone-1-only push (title fix) returns stale server shares and `overwriteFromServer` tombstones the correct locally-derived shares. (b): a fresh device / non-writing participant pulls stale/empty shares and never derives — bill's debts missing from their Balances tab while the claim screen shows the live-derived tab. (c): devices diverge permanently — contradicts "every device converges on identical rows."
  Fix: (a) on `pushExpenses` adoption for `ITEMIZED` expenses where the split wasn't applied, skip share adoption and re-run `materializeShares`; (b) add a `rematerializeBills(groupIds)` call at the end of `SyncEngine.pull()` whenever bill-related tables changed; (c) keep pushing materialized shares through `merge_expense` when the split changed, but treat local derivation as truth everywhere. Don't bump `split_version` from `setClaim`/`setPortion` to force this — that recreates the conflict storm Track F removed.

- [x] **4. New-device sign-in clobbers the server profile with defaults before the first pull.**
  `mirrorCurrentUser` inserts a default `users` row (`"You"`, `baseCurrency="USD"`, null handles/prefs) stamped `now`, then `syncNow` **pushes before pulling** — the fresher timestamp makes `keepNewer` drop the real server row on every later pull. `pull()` also returns early without fetching the user's own `users` row when they have no memberships yet.
  Failure: reinstall + sign in with email OTP on an existing account → display name becomes "You" in every group on every member's device; venmo/cashapp/paypal/zelle handles, preferred payment app, notification prefs, base currency all erased server-side.
  Fix: in `mirrorCurrentUser`, when `existing == null`, `select` the server `users` row first; insert it if present, insert the default only if the server has none. In `pull()`, fetch the caller's own `users` row even when `groupIds.isEmpty()`. Don't weaken `keepNewer` to prefer server rows generally — that breaks Rule 5 for everyone else.

## P1 — serious

- [x] **5. Proxy assignment breaks the "claims partitioned by user" premise: concurrent assignment of the same person wedges sync permanently.**
  Two devices assigning the same (item, user) create two rows with different random PKs; the second's upsert violates the live partial unique index `item_claims_item_user_active_uidx` → 23505 → aborts the entire `push()`, including every table sequenced after `item_claims`. Row stays dirty forever — permanent wedge, surfaced only as generic `Network.Unreachable`. Same risk for `bill_participants` and `shares` re-adds.
  Fix: use deterministic ids for these user-partitioned rows (`"<itemId>__<userId>"` etc., mirroring the `shares` convention) so concurrent writers converge on the same PK and upsert instead of colliding. Also make `pushDirty` per-table-catch so one table's failure doesn't poison the rest. Don't hard-delete the colliding row as "recovery" — Rule 1 violation.

- [x] **6. `merge_expense` has no no-op suppression (unlike the old `commit_expense`) and there's no client push mutex — devices supersede *themselves*.**
  Three independent sync loops (debounced push, realtime pull, 60s `syncNow`) plus `mirrorCurrentUser`'s `syncNow` run with no mutual exclusion. A split edit pushed twice (retry after a lost response, or overlapping loops) → second call sees a stale base → `superseded` → a junk audit row **and a false "your change was superseded" notice to the author whose edit actually won**.
  Fix: server — add the same content-equality (`v_same`) check `commit_expense` has to the `superseded` branch of `merge_expense`; if identical, return `merged` with no audit row. Client — wrap `SyncEngine.push()`/`pull()` in a single `Mutex` so at most one sync op runs at a time. Don't key suppression on `split_updated_by == actor` — a different device of the same user can hold a genuinely conflicting edit.

- [x] **7. Stateless-push causal base silently drops split edits after a lost create-response.**
  `baseSplit = st?.syncedSplitVersion ?: e.splitVersion` — after a lost create-RPC response (no sync-state row) and a subsequent split edit (`splitVersion` 1→2), the next push computes `base = 2` so `client_changed = false` and the edit is dropped with no supersede record.
  Fix: when `st == null`, pre-flight-select the server row; seed sync state from it if present and use its `split_version` as the base. Keep local `splitVersion` as base only when the server row is genuinely absent (clean create).

- [x] **8. Adoption clobbers edits made while the merge RPC is in flight.**
  `pushExpenses` unconditionally `overwriteFromServer(canonical…)` and marks synced at canonical versions — a local edit landing during the round-trip is silently overwritten and never re-dirtied.
  Fix: make `overwriteFromServer` conditional — re-read the expense inside the transaction and skip the whole adoption (+ sync-state stamp) if it no longer matches the pre-push snapshot; depends on fix #6's mutex. Don't adopt the expense but skip shares (splits versions across the entity), and don't stamp synced when adoption is skipped.

- [x] **9. Double-recorded settlements silently over-apply; the overpayment becomes invisible.**
  `applySettlement` validates only against local derived state; allocations sync blind and append-only. Payer + payee (or one offline) both record the same payment → derived remaining goes negative → every outstanding query filters `> 0` so the debt reads "settled" and the double payment vanishes with no signal.
  Fix: (a) add a query for shares with derived remaining `< 0` per group and surface a banner/list linking to `voidSettlement`; (b) re-check `payment ≤ outstanding` inside `applySettlement`'s DB transaction against a fresh read. Don't clamp derived remaining at 0 in SQL — destroys the overpayment signal and corrupts void-restore math.

- [x] **10. `conflicts`/`expense_edit_conflicts` blind-upsert on pull can revert a local resolution and mark it synced.**
  A racing pull (600ms debounce, fires before the 1.2s push debounce) can overwrite a just-resolved local row with the server's still-unresolved copy, then `stampSynced` marks it clean — the resolution never pushes; the conflict card resurrects.
  Fix: before upserting pulled conflict rows, drop any incoming row whose local counterpart has `resolved_at != null` while incoming has `resolved_at == null`; apply the same filter before `stampSynced`. Don't add `updated_at` + `keepNewer` — no schema change needed for a resolution-monotonic filter.

- [x] **11. The OCR rate limiter never engages: client authenticates with the anon key, not the user's token, so the server-side check is always skipped.**
  `ReceiptOcrHttp` sends `Bearer ${ANON_KEY}`; `extract-receipt`'s `auth.getUser()` resolves no user so the entire rate-limit block is skipped for every production call. Live DB confirms `receipt_scan_log` has 0 rows. Anyone with the shipped anon key gets unlimited paid Claude-vision calls; the check also fails open on error and races under concurrency.
  Fix: client sends `client.auth.currentAccessTokenOrNull()` as Bearer (keep `apikey: ANON_KEY`); return `Unavailable` if no session. Server: 401 when `callerId` is null; fail closed on `countError`; insert the scan-log row *before* the Anthropic call. Ship client fix first, then server 401.

- [x] **12. `receipt_scan_log.user_id references auth.users(id)` with no `ON DELETE` will break `delete_my_account()` the moment scan rows exist.**
  `delete_my_account()` never deletes from `receipt_scan_log` before `delete from auth.users` — FK violation once fix #11 makes rows real, while the client wipes local state regardless of server outcome.
  Fix: additive migration — drop and re-add the FK with `on delete cascade`. Must land before #11.

- [x] **13. `superseded_split_edits` has RLS disabled entirely (`relrowsecurity=false`, 0 policies — live-verified).**
  It's missing from the RLS-enable loop. The append-only audit table for superseded money edits (full rejected payloads: amounts, notes, user ids) is freely SELECT/UPDATE/DELETE-able through PostgREST with the anon key.
  Fix: migration — enable RLS, add a single insert-only policy (`for insert to authenticated with check (true)`), and explicitly revoke update/delete from anon/authenticated. Don't add it to the permissive `_rw` loop — that grants the delete you're preventing.

- [x] **14. `push-notify` accepts anon-key callers and pivots to the service role — arbitrary-content push to every device in any group once `FCM_SERVICE_ACCOUNT` is set.**
  Documented in its own header: "send the service-role key **or anon key**." Title/body/data are fully caller-controlled.
  Fix: require the service-role key explicitly at the top of the handler; reject anything else with 403. Must land before the FCM secret is ever configured.

- [x] **15. The uncommitted `onSetServings` teardown/rebuild (BillRoutes.kt) is non-atomic inside a navigation-scoped coroutine.**
  Sequential zero-claims → delete-portions → write-new-portions, each its own repo call and each running `materializeShares`. Navigating away mid-flight cancels after teardown but before rebuild → the item's whole assignment is wiped; other devices can pull the transient empty state.
  Fix: add a single `@Transaction`/`db.withTransaction` repo method (`BillRepository.setServings(...)`) that does teardown + rebuild + one final `materializeShares` atomically; the route becomes one call. Don't just widen the coroutine scope to survive navigation — doesn't survive process death.

## P2 — worth fixing

- [x] **16. RPC create path (`merge_expense`/`commit_expense`) inserts explicit NULLs for any column absent from the client payload via `jsonb_populate_record`, bypassing column defaults — contradicts the additive-migration rule CLAUDE.md relies on.**
  Fix: replace with an explicit column-list insert wrapping post-baseline columns in `coalesce((p_expense->>'col')::type, <default>)`, OR amend CLAUDE.md's migration rule to require new expense columns be nullable. Pick one, update CLAUDE.md in the same commit.

- [x] **17. `editSettlement` voids and re-records in two separate transactions — a crash between them un-pays a recorded payment with no replacement.**
  Fix: add a `SettlementDao.replaceSettlement(...)` as one `@Transaction` combining void + apply; call it once. Don't reorder to write-then-void (double-counts on crash instead).

- [x] **18. `extract-receipt`'s `storagePath` param lets the caller choose the bucket for a service-role download — a private-bucket exfiltration channel the day one exists.**
  Fix: hardcode `from("receipts")`, treat the whole param as the object path (minus an optional `receipts/` prefix), reject any path containing `..`.

- [x] **19. Zone-1 merge and tombstone LWW trust client clocks unbounded (`p_actor` and every timestamp are client-supplied, unauthenticated by the RPC); a future-clocked or crafted payload poisons a field's merge permanently via `updated_at = greatest(...)`.**
  Fix: in `merge_expense`, clamp `v_now` and every incoming `*_updated_at` to `min(value, server_now + 60s)` before use.

- [x] **20. Even-split tip slices of non-claiming participants are silently dropped** — `splitBill`'s `breakdown`/`owedByUser` are built only from users with an item subtotal, so a bill's shares can sum below `amount_subunits` with no reconciliation signal.
  Fix: build `breakdown` over `subtotals.keys ∪ tipShares.keys` (default item subtotal 0). Update `BillSplitTest` expectations.

- [x] **21. A bill's total can be zero or negative with no validation** — an oversized discount produces a negative-amount expense, violating the "always positive" entity invariant, hidden by the `> 0` outstanding filters.
  Fix: in `BillRepositoryImpl.validate`, compute the same `total(...)` and reject `<= 0` with a field error on `discount`.

- [x] **22. `selectIn` builds one `id=in.(…)` GET per table with every expense id — at ~800-1000 expenses/group the URL exceeds gateway limits and every pull fails wholesale, reported as permanently "unreachable."**
  Fix: chunk `values` into batches (e.g. 100 ids) and concatenate results inside the `selectIn` helper. Don't switch to unfiltered full-table selects as a workaround (breaks post-RLS-tightening).

- [ ] **23. STILL OPEN, and half of it must NOT be "fixed".** Four unresolved `expense_edit_conflicts` rows on the live server are stranded: invisible in-app but synced to every device forever.
  **Not a defect:** `observeEditConflicts` returning empty is deliberate and documented (`data/AGENTS.md:118`), and asserted by `EditConflictResolutionTest.observeEditConflicts_isEmpty_bilateralCardsRetired`. Leave it.
  **Genuinely open, needs the owner:** (a) the 4 live rows carry full rejected payloads, so they need exporting for a manual keep/apply decision before being marked resolved via SQL — that needs live DB access, which this session did not take; (b) removing `expense_edit_conflicts` from `SyncEngine.pull`/`push` and `SyncManager.SYNC_TABLES` is **deliberately deferred** — the owner asked to leave it until the concurrent `RowSyncState` work settles (asked and answered 2026-08-15).

- [x] **24. Sign-out doesn't clear Room; sign-in as a different account on the same device pushes account A's stale rows to the server under account B's session.**
  Fix: on `signOut`/`deleteAccount`, clear synced Room tables + `row_sync_state`/`expense_sync_state`, gated on a dirty-check ("unsynced changes will be lost" warning first). Don't wipe unconditionally in the same path that runs when the delete RPC failed.

- [x] **25. `runCatchingSync` maps every failure (serialization drift, RLS denial, unique-index violation) to generic `Network.Unreachable` — a permanently failing push (e.g. finding #5's wedge) looks identical to airplane mode; `SyncManager` swallows the result entirely.**
  Fix: map Postgrest/HTTP-status exceptions to `AppError.Backend(status, code)`, keep `Network.Unreachable` for transport failures only; add a `MutableStateFlow<SyncHealth>` (consecutive-failure count + last error kind) observable from Settings/debug UI.

- [x] **27. ~~The realtime publication omits `users`~~ — WON'T FIX. This finding is wrong and acting on it re-creates a production outage.**
  `AGENTS.md` §4.3 and `supabase/schema.sql` both forbid adding app tables to the `supabase_realtime` publication. Profile renames riding the 60s fallback tick is the intended trade, not a defect. **Do not rediscover this as actionable.** (Closed 2026-08-15.)
