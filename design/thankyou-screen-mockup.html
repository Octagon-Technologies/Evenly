Evenly — feedback thank-you screen, three variants

Per THANKYOU_SCREEN_PROMPT.md: one screen, three treatments selected by feedback Type. Same frame and blue system as the claim flow (app.css tokens, IBM Plex Sans) so it reads as one product with /feedback and the web claim flow rather than the marketing site's serif system. Mobile is the design; desktop is the same layout in a centred column, not a rebuild. Everything below is drawn with transforms, opacity and one stroke-dashoffset draw-on per icon — all achievable in Compose. Press Replay on any artboard to watch the animation again.

Mobile · the three variants

Settle, lift, travel

One shared shape — back arrow, centred icon, headline, subhead, full-width button — carrying three distinct motions and icons rather than three distinct layouts. That's the answer to the brief's Q1: fully separate treatments would triple the surface to build and audit for three screens someone sees for two seconds; a shared frame with a distinct moment per type gets the emotional differentiation without three maintenance burdens. Colour stays inside the app's existing blue system throughout, on purpose (see notes below) rather than reaching for a new hue per variant.

Notes, and what's still open

Decided: one shared frame, three motions (Q1). No submitted-content summary shown back to the user (Q2) — the message they just typed is still on the screen behind this one, and re-displaying it here adds weight to what the brief asks to keep light. No ticket reference number in v1 (Q3) — nothing in ADMIN_FEEDBACK_SPEC.md exposes one to the submitter, and inventing one to show here would be a promise ("check ticket #4021") the queue doesn't back yet. Reply-time language stays at "we'll reply by email" (Q5), no number, matching the spec's v1-is-manual resolution flow. The anonymous-Problem case (Q6) is handled by dropping the email clause, not by a fourth variant.

Still open: the exact onward action for the web claim flow's footnote entry point (brief's Q4) — "back to the bill" only makes sense if the claim screen is still live in another tab or the same view; needs a decision once the footnote link's own presentation (new tab vs. inline) is settled in WEB_CLAIM_SPEC.md-adjacent work. Icon set above is a first pass, not final art — worth a look from whoever owns the feather mark treatment before Compose work starts, so the icon language matches EvWordmark.kt's line weight rather than this mock's plain SVG strokes.
